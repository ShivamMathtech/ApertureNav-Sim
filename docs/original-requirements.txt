# MASTER DEVELOPMENT PROMPT

## Build a Complete ROS 2 + Gazebo Drone Aperture Navigation Simulator

You are a senior multidisciplinary robotics engineering team consisting of:

- ROS 2 architect
- Gazebo simulation engineer
- UAV/drone controls engineer
- computer vision engineer
- robotics perception engineer
- path-planning engineer
- 3D geometry engineer
- PX4 integration engineer
- Python developer
- C++ developer
- full-stack engineer
- UI/UX engineer
- DevOps engineer
- QA/testing engineer
- robotics researcher

Your task is to design and implement a complete, modular, production-quality simulation platform called:

# ApertureNav-Sim

## Autonomous Drone Aperture Detection, Alignment, and Confined-Space Navigation Simulator

The simulator must allow a quadrotor to detect and navigate through small openings such as:

- windows
- square frames
- rectangular frames
- circular openings
- ventilation openings
- door-like gaps
- broken-wall openings
- custom apertures
- rotated frames
- partially obstructed openings

The project is simulation-first and intended for robotics research, education, algorithm development, perception experiments, motion planning, and controller evaluation.

Do not assume a physical drone is connected.

# 2. PRIMARY SYSTEM OBJECTIVES

The simulator must:

1. Launch Gazebo automatically.
2. Spawn a configurable quadrotor.
3. Load configurable indoor environments.
4. Simulate RGB camera.
5. Simulate depth camera.
6. Simulate IMU.
7. Simulate odometry.
8. Optionally simulate LiDAR.
9. Detect apertures/windows.
10. Estimate aperture geometry.
11. Estimate 3D aperture pose.
12. Calculate whether the drone can fit.
13. Approach the target opening.
14. Align position and heading.
15. Generate a trajectory through the aperture.
16. Execute the trajectory.
17. Avoid frame collision.
18. Abort when conditions become unsafe.
19. Visualize everything in RViz.
20. Expose telemetry to a professional UI.
21. Record complete experiment data.
22. Generate post-run analytics.
23. Reset and rerun scenarios without restarting the entire stack.

1. User launches one command.
2. Gazebo opens.
3. Drone spawns.
4. Indoor environment loads.
5. Camera begins publishing.
6. Depth sensor publishes.
7. Aperture is detected.
8. 3D aperture pose is estimated.
9. Clearance is calculated.
10. Mission manager selects approach.
11. Planner generates trajectory.
12. Drone moves toward the aperture.
13. Drone aligns.
14. Safety monitor validates clearance.
15. Drone enters slowly.
16. Drone crosses the frame without collision.
17. Drone reaches post-entry point.
18. Mission state changes to COMPLETE.
19. Experiment data is saved.
20. Dashboard displays results.
21. Reset allows another run.

# 64. OUTPUT EXPECTATION FROM THE CODING MODEL

Do not only explain architecture.

Actually generate the repository.

For every development phase:

1. Show the files being created.
2. Provide complete source code.
3. Keep package dependencies correct.
4. Keep launch files synchronized.
5. Keep README commands updated.
6. Build-test the project.
7. Fix discovered errors.
8. Never replace working code with pseudocode.
9. Never leave critical modules unfinished.
10. Produce a final project that can run from a fresh documented setup.

At the end, provide:

```text
full repository tree
setup instructions
build instructions
run instructions
test instructions
architecture explanation
ROS topic map
TF tree
parameter reference
troubleshooting guide
experiment workflow
```

The implementation must prioritize stability, modularity, reproducibility, and simulation safety over unnecessary complexity.
